# OCR 문서 교정 및 정제 규칙 가이드 (Document Restoration Rules Guide)

본 문서는 스캔 도서의 OCR 추출 과정에서 발생한 텍스트 오염, 자모 분리, 임의 줄바꿈 및 레이아웃 노이즈를 제거하고 완벽한 문장 형태로 복원하기 위해 오늘 정의하고 적용한 **문서 교정 및 정제 규칙**을 정리한 자료입니다.

---

## 1. 개요 및 복원 목표

* **입력 소스**: 스캔 이미지에서 OCR로 추출하여 글자 깨짐, 오타, 불필요한 줄바꿈, 페이지 구분 기호 및 머리말/꼬리말이 섞여 있는 불완전한 텍스트 파일
* **최종 출력**: 가독성이 극대화되고 가공·재활용이 편리하도록 레이아웃 노이즈가 제거되고 문장이 매끄럽게 연결된 **순수 플레인 텍스트(Plain Text)**
* **핵심 복원 대상**:
  1. 한글 맞춤법 및 띄어쓰기 오류 교정
  2. OCR 텍스트 깨짐(쓰레기 기호) 소거 및 유실 문자 복원
  3. 페이지 표시(`[페이지 X]`) 및 점선 구분선 제거
  4. 본문 중간에 섞여 든 머리말/꼬리말(쪽수 및 반복 목차명) 제거
  5. 페이지 경계 및 임의 구분선으로 인해 잘려나간 어절(단어) 결합

---

## 2. 문서 교정 및 정제 알고리즘

### 2.1. 페이지 단위 파싱 및 마커 식별
문서 내에 존재하는 페이지 경계를 명확히 분할하기 위해 정규 표현식을 사용하여 페이지 번호와 구분선을 식별합니다.

* **페이지 마커 정규식 패턴**:
  ```python
  pattern = r"(\[페이지\s+(\d+)\]\n─+\n)"
  ```
* **매칭 예시**:
  ```text
  [페이지 12]
  ────────────────────────────────────────────────────────────
  ```

### 2.2. 문장 완결 기준 청크 병합 (Semantic Chunking)
단순히 글자 수나 페이지 단위로 기계적으로 쪼개서 LLM에 보낼 경우, 청크와 청크가 만나는 경계선에서 단어(어절)가 다시 잘려 복원되지 않는 문제가 발생합니다. 이를 방지하기 위해 **문장이 온전하게 마침표로 끝나는 페이지 경계**를 기준으로 청크(3~5페이지 묶음)를 병합하여 전송합니다.

* **청크 경계 종결 문자 기준**:
  마지막 문자열이 `.`, `?`, `!`, `"`, `”`, `』`, `〉`, `)` 또는 한국어 종결 어미인 `'다'`로 끝날 때 분할점(split point)으로 인정합니다.
* **병합 알고리즘 구현 로직**:
  ```python
  chunks = []
  current_chunk_pages = []
  current_chunk_len = 0
  
  for page in pages:
      current_chunk_pages.append(page)
      current_chunk_len += len(page["text"])
      
      body_strip = page["text"].strip()
      is_sentence_end = False
      if body_strip:
          last_char = body_strip[-1]
          is_sentence_end = last_char in ['.', '?', '!', '"', '”', '』', '〉', ')', '다']
          
      # 조건: 최소 3페이지(또는 2,500자 이상) 확보 및 문장 종결 (단, 최대 5페이지 초과 시 강제 분할)
      if (len(current_chunk_pages) >= 3 or current_chunk_len >= 2500) and (is_sentence_end or len(current_chunk_pages) >= 5):
          chunks.append(current_chunk_pages)
          current_chunk_pages = []
          current_chunk_len = 0
  ```

## 3. LLM 정제 규칙 및 프롬프트 엔지니어링

교정의 일관성을 확보하고, AI가 임의로 철학적 문장이나 어휘를 창작(할루시네이션)하는 것을 방지하기 위해 다음과 같은 지시 사항을 Claude 모델(`claude-haiku-4-5-20251001`)에 전달하여 `temperature=0.0`으로 실행했습니다.

### 3.1. 교정 프롬프트 (v2 - Clean Layout 버전)

```markdown
아래는 책의 여러 페이지가 결합된 OCR 추출 텍스트입니다.
다음 규칙에 따라 텍스트를 완벽하게 정제하여 복원해 주세요:

1. 모든 페이지 표시(예: "[페이지 11]")와 구분선(예: "────────────────────────────────────────────────────────────")을 완전히 삭제하세요.
2. 페이지의 상단이나 하단에 반복적으로 나타나는 머리말, 꼬리말, 쪽수 표시(예: "이 책의 활용법 11", "12 우울한 날엔 니체")를 찾아내어 완전히 제거하세요. 본문 흐름과 관련 없는 불필요한 메타데이터입니다.
3. 페이지가 전환되는 경계선 주변에서 단어가 반으로 쪼개져 강제로 줄바꿈된 부분(예: "성\n\n이 책의 활용법 11\n\n[페이지 12]\n───...\n찰" -> "성찰", "문\n\n12 우울한 날엔 니체\n\n[페이지 13]\n───...\n제를" -> "문제를")을 올바르게 판단하여 띄어쓰기 없이 한 단어로 이어 붙이세요.
4. 글자 깨짐, 오타, 자모 분리, 조사 및 어미 오류를 교정하여 한글 맞춤법과 띄어쓰기에 맞는 완벽한 문장 형태로 복원하세요.
5. 오직 정제 및 복원된 최종 텍스트만 출력하고, 설명이나 코멘트는 일체 작성하지 마세요.
```

## 4. 구체적 예시 기반 비교 분석

### 4.1. 메타 데이터 및 쪽수 제거
* **오염된 원본:**
  ```text
  ... 기쁨을 발견할 것이다.
  
  이 책의 활용법 11
  
  [페이지 12]
  ────────────────────────────────────────────────────────────
  찰의 노력 없이는 ...
  ```
* **정제 결과:**
  ```text
  ... 기쁨을 발견할 것이다.
  
  성찰의 노력 없이는 ...
  ```
  *(해석: 페이지 11 끝의 쪽수와 페이지 12 마커, 구분선이 일괄 소거되고 끊어졌던 '성'과 '찰의'가 '성찰의'로 유기적으로 결합됨)*

### 4.2. OCR 변환 깨짐 및 괄호 노이즈 제거
* **오염된 원본:**
  ```text
  소설 『재의 고리(ᄂᄒ 0600「68)』가 있으며, 홈페이지(04 68141368『-47007855.1)에서...
  ```
* **정제 결과:**
  ```text
  소설 『재의 고리』가 있으며, 홈페이지에서...
  ```
  *(해석: OCR 판독 오류로 인해 괄호 안에 유입된 무작위 기호와 깨진 알파벳, 숫자를 문맥에 근거하여 자동 판단해 제거함)*

### 4.3. 어색한 줄바꿈 수정
* **오염된 원본:**
  ```text
  독일계 프랑스인으로 철학 교수 자격을 가지고 있 구하는 삶에 앞서 재즈 피아니스트
  로서 명성을 얻은 바 있는 그는...
  ```
* **정제 결과:**
  ```text
  독일계 프랑스인으로 철학 교수 자격을 가지고 있으며, 철학을 추구하는 삶에 앞서 재즈 피아니스트로서 명성을 얻은 바 있는 그는...
  ```
  *(해석: 단어 사이의 불필요한 줄바꿈을 문장 성분에 맞게 이어 붙이고, 문맥상 생략되거나 깨진 어절인 '가지고 있 구하는'을 자연스러운 연결형 어미인 '가지고 있으며, 철학을 추구하는'으로 완전하게 교정함)*

## 5. 결론 및 향후 적용 가이드

* **이후 작업 시 유의점**: 
  1. 도서마다 상/하단 머리말 및 쪽수의 규칙이 다릅니다. (예: `[쪽수] [책 제목]`, `[챕터명] [쪽수]` 등)
  2. 따라서 LLM 프롬프트의 **규칙 2번** 예시 부분(`"이 책의 활용법 11", "12 우울한 날엔 니체"`)을 해당 도서의 고유한 반복 패턴으로 일부 변경해 줄 때 가장 정교한 제거 성능을 보여줍니다.
  3. API Rate Limit을 방지하기 위해 대용량 배치 처리 시에는 반드시 `time.sleep(0.3)` 정도의 적절한 API 호출 간 딜레이를 부여해야 중단 없는 파이프라인 처리가 가능합니다.
