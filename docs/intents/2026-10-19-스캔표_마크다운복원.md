# Intent: 스캔 PDF 표를 Markdown 표로 복원 (로컬 OCR)

## 1. 배경 및 문제
- 현재 문제: 스캔 문서 `01_입력/20140312_SI 영업 및 수행에 대한 운영방안.pdf`(5쪽, 텍스트 레이어 없음)를 `rapidocr_first` 모드로 처리한 결과(`02_결과/20261019_143847_…운영방안.txt`, Vision 0쪽)에서 표가 전부 풀려 나왔다.
  - 5쪽 「프로젝트 인벤토리 관리」: 프로젝트명 14개가 한 줄로 붙고, 이어서 `3월 / 8,000 / 1,000 / 500 …` 처럼 숫자가 한 칸씩 세로로 나열됨 → 어느 숫자가 어느 프로젝트·어느 열인지 알 수 없음
  - 1쪽 「목표와 역할」: `도전목표 / 14.2억원 / 30억원 / 378억원 …` 이 행·열 구분 없이 흩어짐
  - 2쪽 「상태」표: 번호·상태·설명이 뒤섞여 `… 1 가득 ※수주/계약 … 2 가동 …` 형태
  - 결과 파일 어디에도 `[표 N]` 표식이 없음 → 엔진의 격자선 기반 표 감지(`core/figure_detector.py` `_detect_tables` → `_extract_table_markdown`)가 이 문서에서 표를 못 잡았거나, 잡은 뒤 버린 것으로 **추정**(원인 실측은 §8)
- 영향받는 업무/사용자: 사내 보고서·기획서처럼 표가 많은 스캔 문서를 텍스트로 받아 읽거나 OKF 지식위키에 넣는 사용자. 숫자가 어느 행·열에 속하는지 원본을 다시 열어야만 알 수 있다.

## 2. 목표
- 달성하려는 결과: 스캔 문서의 격자 표를 **Markdown 표**(`| 열 | 열 |`)로 출력해, 텍스트 파일만 보고도 행·열을 구분해 읽을 수 있게 한다. **이 PDF는 시험 표본**이고 개선은 엔진 일반에 적용한다.
- 성공 기준(이 PDF 기준, 로컬 엔진만):
  1. 표 4개가 각각 Markdown 표로 출력된다 — 1쪽 목표와 역할, 2쪽 상태표, 5쪽 프로젝트 인벤토리, 5쪽 프로젝트 수행 현황
  2. 5쪽 인벤토리 표: 데이터 14행 + 합계 1행, 7열(프로젝트명·영업대표·고객·발주예정월·발주금액·수주금액·매출액)이 원본과 행·열 대응 일치. 숫자 칸 원본 대비 일치율 **95% 이상**
  3. 2쪽 상태표: 4행 × (번호·상태·설명), 칸 안 여러 줄 설명이 한 칸에 모인다
  4. 표 밖 본문은 지금 결과와 같거나 나아진다(표 영역 글자가 본문에 중복·누락되지 않음)
  5. 회귀 없음: `python -m pytest engine/tests` 전부 통과 + 기존 책 표본에서 표 오탐(본문을 표로 바꿈)이 늘지 않음

## 3. 범위
### 포함
- 격자선이 있는 스캔 표의 감지·행열 복원·Markdown 출력 (`rapidocr_first` 경로)
- 병합 셀(1쪽 「목표 및 평가KPI」 세로 병합, 「SI영업」 가로 병합) — 병합 칸 값은 첫 칸에 두고 나머지는 빈칸
- 칸 안 여러 줄 글자를 한 칸으로 합치기
- `.txt`·`.md` 출력 모두 같은 Markdown 표 사용
- 간트차트·결재란 등은 **글자 칸만** 표로 남긴다(5쪽 수행현황의 이름·상태·프로젝트명·가득률 숫자 등)

### 제외
- Vision LLM(Gemini·Claude·Ollama) 사용 — 로컬(RapidOCR·OpenCV)만
- 막대·화살표·서명·도장 같은 비글자 요소 표현(`[그림]` 표식도 넣지 않음)
- 격자선이 없는 표(공백 정렬만 된 표)
- 디지털 PDF(텍스트 레이어) 경로·OKF 지식위키 쪽 코드
- 표 밖 본문 서식(글머리 ○·- 줄바꿈, 누락 글자) — §8 질문 참조

## 5. 제약 조건
- 로컬 무료 엔진만(RapidOCR 한글 v5 + OpenCV). 새 외부 패키지 추가는 구현 계획 승인 때 따로 확인
- 기존 표 오탐 방지 규칙(`figure_detector.detect` 의 「행 절반 이상이 한 칸이면 표가 아니다」, 예측기계 54·107·133·135쪽 사례)을 깨지 않는다
- 처리 시간: 쪽당 증가폭을 측정해 보고(기준은 계획 단계에서 합의)
- bat·py 작성 규칙(CRLF·UTF-8, `-X utf8`) 준수

## 6. 주요 프로세스
1. 쪽 이미지에서 격자 표 영역 감지
2. 표 영역의 가로·세로 선으로 칸(셀) 격자를 구하고, 병합 칸을 판정
3. 칸마다 RapidOCR 글자 상자를 배정·합쳐 칸 글자를 만든다
4. Markdown 표로 만들고 본문에서는 그 영역을 가린 뒤 `[표 N]` 자리에 끼워 넣는다
5. 결과 파일에 표가 원래 위치(본문 흐름 순서)에 나온다

## 7. 예외 및 리스크
| 상황 | 처리 방향 |
|---|---|
| 선이 흐리거나 끊긴 스캔 표 | 감지 실패 시 지금처럼 본문 텍스트로 남김(글자 손실 없음이 우선) |
| 칸 격자가 불규칙(병합 다수) | 행·열 수가 원본과 달라도 글자는 버리지 않는다 — 무손실 가드(표 결과에 원 글자 95% 이상) |
| 본문 단락·도식을 표로 오인 | 기존 오탐 방지 규칙 유지 + 책 표본 회귀 측정 |
| 간트 막대 칸(빈 칸·화살표) | 빈칸으로 둠 |
| 처리 시간 증가 | 측정 후 보고, 과하면 표 감지된 쪽에만 적용 |

## 8. 미해결 질문
- ~~원인 실측 미완~~ → **실측 완료(2026-10-19, 300dpi, `_detect_tables`·`_extract_table_markdown` 직접 호출)**:
  1. **감지는 된다** — p1 1개·p2 1개·p5 3개(그중 1개는 제목 띠, 글자 0) 영역. p3·p4 0개(표 없음, 정상)
  2. **행·열 복원이 깨진다** — `_extract_table_markdown` 이 격자선을 쓰지 않고 「세로로 겹치는 글자 상자 = 같은 행」으로 묶는다. 기울어진 스캔에서 행이 연쇄로 겹쳐 p5 인벤토리 15행이 **2행**으로, p1 표가 23칸 1행으로 뭉쳤다. 열은 칸 경계 없이 글자 상자 순서라 행마다 열 수가 다르다
  3. **결과 파일에서 표가 버려진다** — 정제 저장 경로(`ocr_gradio.py` 772·1383·1538행 `writer.write_plain(clean_pages(corrected_text))`)는 `page.figures`(`[표 N]` 자리표시)를 쓰지 않는다. 표 자리표시는 정제 안 한 `writer.write()` 경로에만 「비텍스트 영역」으로 쪽 끝에 붙는다
  4. **본문에 표 글자가 그대로 남는다** — `_mask_regions` 가 표 영역 안 확실히 읽힌 단어를 원본 픽셀로 되살려, 본문 OCR 이 표 글자를 다시 풀어 읽는다(결과 파일의 풀린 숫자 나열이 이것)
- 표 밖 본문 문제도 같이 다룰지: ① 1쪽 ○ 글머리 11줄이 한 덩어리로 붙음 ② 4쪽 「인력투입없는 장비사업 : 10%」의 `10%` 가 결과에서 빠짐(글자 누락) — 이번 범위는 표만으로 두었음
- 1쪽 결재란(팀장·본부장 + 서명)은 표로 낼지, 「팀장 / 본부장」 글자만 둘지
- 회귀 측정에 쓸 「기존 책 표본」 범위(예측기계 등 몇 권·몇 쪽)

**고친 원인 4가지**: ① 행·열 복원을 글자 상자 배치 기준(선은 보조)으로 다시 씀 — `figure_detector._extract_table_markdown` ② 표로 바꾼 영역의 글자는 본문에 되살리지 않음 ③ 표 자리 표지(`⟨TABLE:쪽-번호⟩`)를 본문 높이에 끼우고 저장 직전 Markdown 표로 바꿈 — 정제 경로(`_CleanCheckpoint.finish`·`write_plain`)도 포함 ④ 150dpi 렌더에서 흐린 바깥 테두리를 놓쳐 표 상자가 좁게 잡히던 것을 테두리까지 넓힘(이웃 표 상자 앞에서 멈춤).

**알려진 한계**: 5쪽 간트 표의 가동률 숫자가 한 칸에 붙어 나옴(「40507080」 — 월 칸 OCR 상자가 합쳐짐) · 1쪽 「목표및」이 빈 행으로 따로 나옴 · 표 칸 OCR 을 2배로 키워 읽어 표 있는 쪽 처리 시간이 늘었다(이 PDF 5쪽 기준 약 60~75초).
